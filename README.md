# TextFixer

First test build of a Windows tray writing assistant.

Agreed design: .NET 10 WinForms shell, WebView2 review window, plain HTML/CSS/JavaScript, Ctrl+Alt+- selection capture, explicit review and replacement, and ChatGPT plan sign-in. No frontend build or Node runtime.

This is an experimental test build. Live authentication and Chrome editing need interactive verification with the user's account.

## Build and run

Requires the .NET 10 SDK to build. Run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/publish.ps1` (or `build.ps1`), then open `artifacts/TextFixer/TextFixer.exe`. There is no npm, frontend build, or Node runtime. Keep the whole output folder together. Running this framework-dependent test build requires the .NET 10 Desktop Runtime and Microsoft Edge WebView2 Runtime.

Publishing now uses `scripts/publish-swap.ps1`, copied and adapted from the hot-swap-update skill. It builds beside the install folder, renames locked code files with a timestamp, and moves in the new build without terminating the app. UI files are embedded in the assembly. An existing instance keeps running its old version; the next normal start runs the update. The legacy loose `Web` folder is preserved for the first transition so a currently running older build retains its page files. New code does not read that folder.

Locked retired files are retained and retried for cleanup on a later publish. This environment's wrapper skips reboot/sign-in cleanup registration because it cannot write those system/user settings. App state, credentials and Chrome registration manifests are stored under `%LOCALAPPDATA%\TextFixer`.

The skill is available project-locally at `skills/hot-swap-update/SKILL.md`, referenced by `AGENTS.md`. Global installation into `C:\Users\JPS\.codex\skills` was denied by the filesystem sandbox. `install-codex-skill.ps1` is prepared for execution outside that restriction.

The window opens on first launch. TextFixer has no taskbar button; it lives in the tray. Settings > Startup > "Start with Windows" (off by default) adds a current-user Run entry; a start with Windows opens no window and waits in the tray. Closing or minimizing the window hides it to the tray; double-click the tray icon to reopen, or choose Exit from the tray menu to stop the app. Open (default Ctrl+Alt+., AltGr+. on German keyboards) captures the selection and shows a task choice: Review, Translate, Fact check, Summary, Explain or Rewrite; nothing is sent until a task is chosen. Review has the default shortcut Ctrl+Alt+- (AltGr+-). Both keys follow their label, so "-" is right of 0 on US keyboards and left of the right Shift on German ones; neither types a character on German or US layouts. Review starts right away. The other tasks start without a shortcut; each can get one in Settings > Shortcuts, which then captures and runs the task's main action right away (Rewrite improves the text, Fact check checks without context). Startup reports any shortcut another app has registered.

Settings > Shortcuts lists Open, Review, Translate, Fact check, Summary, Explain and Rewrite (the sidebar order). Click a shortcut, press the new keys (Esc cancels); Remove clears an optional one, and Open always keeps one. A shortcut is Ctrl and/or Alt, optionally Shift, with A to Z, 0 to 9, the period, comma or minus key (by label, VK_OEM_PERIOD, VK_OEM_COMMA, VK_OEM_MINUS; not the keypad minus) or F1 to F24 (`Services/Shortcuts.cs`). Refused: duplicates between the tasks, Ctrl+A/C/V/X/Y/Z (editing, and TextFixer sends Ctrl+C and Ctrl+V itself), Alt+F4, Ctrl+Alt combinations that type a character on the current keyboard layout (AltGr, checked with `ToUnicodeEx`), and combinations another app has registered. `Native/HotkeyManager.cs` registers only the set shortcuts (hotkey ids 46 to 52 in task order). While a shortcut is being recorded it unregisters all of them so the keys reach the window; they return after the change, on Esc, when the window or Settings closes, and after 30 seconds at the latest. A rejected change keeps the previous registrations. Changes apply immediately and are stored as `shortcuts` in `settings.json`: text such as "Ctrl+Alt+K", or null for a task without a shortcut. An invalid entry keeps its default; a saved set with duplicates falls back to all defaults. The tray tooltip, Help and window texts show the current shortcuts.

## Review mode

Settings > Review (stored in `%LOCALAPPDATA%\TextFixer\settings.json` as `reviewMode`):

- **One request for all tabs** (default): one ChatGPT request returns the corrected text, the labelled corrections and the Worth checking findings.
- **One request per tab**: five focused requests (Spelling, Grammar, Punctuation, Wording, Worth checking) are sent at the same time; Formatting is checked locally. A full check takes about as long as the slowest single request. Each request fixes only its own category (`ReviewPrompt.FocusedInstructions`). The app sends one `tabProgress` listing all running tabs, then a `tabResult` as each answer arrives, in any order; the window marks tabs ready, running (spinning ring), failed (`!`) or stopped, and finished tabs can be reviewed while the rest run. Results are merged in `focusParts` (`app.js`): where two tabs change the same characters, the tab further left wins; changes that only touch the same word (for example a capital letter and a following comma) are kept as separate character-level edits. Decisions made while later tabs run are kept. Copy and paste unlock when all requests finish. A failed tab is reported and skipped; sign-in problems and an exhausted usage limit cancel the other requests and stop the run. This mode uses about five times the plan allowance of a single review.

## Clipboard history

TextFixer keeps your last 20 copied texts (Clipboard history at the bottom of the left sidebar). Each entry has "Copy plain" (text only) and, when it was copied with HTML or RTF, "Copy formatted" (text plus the saved HTML and RTF); these buttons are the only way to copy an entry, and clicking the entry text does nothing. The × in the corner removes an entry. A request without `plain:false` copies plain text. Copying the same text again moves its entry to the top. Images and files are not recorded. Content marked `ExcludeClipboardContentFromMonitorProcessing` or `CanIncludeInClipboardHistory = 0` (password managers, TextFixer's own temporary Ctrl+Alt+- data) is skipped, as are texts over one million characters. The history is stored in `%LOCALAPPDATA%\TextFixer\clipboard-history.bin`, DPAPI-encrypted for the current Windows user. Settings > Clipboard history turns recording on or off (on by default; turning it off deletes the history) and clears it. The setting lives in `%LOCALAPPDATA%\TextFixer\settings.json`. Offline tests: `dotnet run -c Release --project tests/ClipboardHistoryTests`.

## First test

1. Click "Continue with ChatGPT" and finish authorization in the system browser. The app waits for the callback; Stop ends the wait.
2. In a disposable Chrome text field, type a paragraph, select it, and press Ctrl+Alt+-. Release both keys.
3. The captured selection is sent for review automatically after capture when ChatGPT is connected.
4. Review suggestions in the Spelling, Grammar, Punctuation, Wording and Formatting tabs; Worth checking has a section of its own below the corrections. Accept or reject individual changes. Reasoning rewrites require an explicit "Use this wording" action.
5. Choose "Paste with formatting", a "Copy as" format ("Original formatting" keeps the copied HTML exactly), or the explicit plain-text option. Replacement returns focus, copies the selection again, and aborts if it no longer matches. Check the editor result. Ctrl+Z in the editor should undo a normal paste.
6. Also test changed selections, a closed target window, multiple Chrome tabs, multiline text, and clipboard restoration before using it on important text.

Only the selected or pasted text is sent, up to 30,000 characters. Text inside password fields is generally not copyable; do not use this app for secrets. The app never submits or sends posts or emails.

Ctrl+Alt+- captures any selection the active app can copy. At capture, Windows UI Automation reports whether the focused element accepts typing. Selected text in a read-only document (for example a web page paragraph) gets "Copy" only; editable fields and content-editable editors keep "Paste". When the answer is unclear, both actions stay available. A failed capture writes the app name and reason (never text) to `%LOCALAPPDATA%\TextFixer\diagnostics.log`.

A status-bar icon identifies a Chrome or Ctrl+Alt+- capture, with its source in the tooltip. Ctrl+Alt+- remains a clipboard workflow; direct editing is available after an extension capture. When the clipboard includes valid HTML, Ctrl+Alt+- retains that original fragment, patches only accepted text corrections into its text tokens, and offers "Paste with formatting" or "Original formatting" under "Copy as". Original paragraph elements, empty elements, inline formatting, attributes and styles remain intact. CF_HTML offsets are recalculated in UTF-8 bytes. Cross-format edits or HTML/plain-text mismatches are rejected without an automatic plain-text fallback. Plain-text replacement requires the explicit checkbox and is enforced in C#.

The companion extension is plain JavaScript, without a build step. Setup is once per Windows user:

1. Open `chrome://extensions` in Chrome, enable Developer mode, choose Load unpacked, and select the project's `chrome-extension` directory.
2. The bundled manifest key gives it the fixed ID `hpmehbmdgfpgoggpemlefhfmbjeedpop`. Verify this is the ID Chrome displays.
3. Run `powershell -File install-chrome-bridge.ps1` from the project directory. It registers only that extension for the new executable using a current-user native messaging registry entry. This setup script has been supplied, not run automatically.
4. In a disposable text field or supported contenteditable editor, select a passage and right-click "Review selection in TextFixer". Check the result in the desktop app, then choose "Apply in Chrome".

This route does not use the clipboard. It computes accepted correction ranges locally, validates the complete original editor text, preflights rich-text ranges, and applies small native text editing commands from end to start. Untouched paragraph and formatting elements are retained. Corrections that cross text-node/formatting boundaries or change line breaks are refused. Navigation, disconnection or changed text invalidates the capture; identical-text re-renders are allowed. Nonbreaking and regular spaces compare equivalently without changing offsets; NBSP-only suggestions are omitted. Each edit is checked for a stable expected result, polling for up to one second to allow asynchronous editors to update. At most 200 corrections can be applied per batch. There is no automatic clipboard fallback after a direct edit fails.

Accepted corrections are trimmed to their smallest differing character range without splitting Unicode surrogate pairs. Before sending a direct edit, the extension yields for editor selection handlers and verifies the exact selection and text again. It stops between edits at a 60-second batch deadline, reporting how many corrections were applied, before the desktop's 90-second timeout. Reload the extension in `chrome://extensions` after updating its files.

Some rich editors intercept or transform commands. If an editor rejects a correction midway through a batch, earlier corrections may already be applied. Check the editor and use its Undo before retrying. Undo grouping is editor-dependent. Canvas-based editors such as Google Docs are not supported by this first bridge. No universal compatibility or zero Unicode-error guarantee is made. Ctrl+Alt+- uses clipboard replacement, with original HTML retained when available.

The extension starts a native-host mode of the same executable. It relays framed UTF-8 JSON over a current-user-only named pipe to the tray app. Credentials stay in the tray process. Host registration validates the exact extension origin and executable path. Move the executable only after re-running registration for the new path.

## Editing limits

Capture and replacement use Ctrl+C and Ctrl+V, not accessibility writes. Common clipboard formats are saved and restored, provided the clipboard has not changed independently. Private/delayed formats may not survive. Temporary text written by TextFixer requests exclusion from clipboard history/cloud sync; the source app's own copy operation may still enter history.

HTML clipboard capture now preserves the original fragment and changes only safely mapped text ranges. Both the original paragraph markup and Unicode text are offered to the destination. RTF is patched the same way (`Native/RtfClipboard.cs`): the copy keeps its RTF, and Copy and Replace offer it next to the HTML with the corrections written into its text runs, so Word, Outlook, WordPad and rich text fields get their own format back. An RTF-only copy keeps its formatting this way; when the corrections do not fit the RTF (its visible text differs from the plain text, or a correction crosses a formatting change), the RTF is left out, and an RTF-only copy asks for plain-text replacement. Formatting fixes exist only for HTML, so a paste with them leaves the RTF out. Markup typed as text (Markdown, BBCode, HTML tags, Reddit and Discord syntax, URLs, hashtags, mentions; `Services/MarkupGuard.cs`) is never changed by a correction: Copy and Replace refuse a correction that touches it and name it. Destination applications may ignore rich clipboard formats or normalize the pasted HTML. Paste uses delayed rendering: restoration occurs only after a supported-format read from the target process has been observed, with a short grace period. If the read cannot be attributed to that process within five seconds, the revision stays on the clipboard and a notice asks you to check the editor. Read confirmation does not prove that the editor accepted the paste.

Delayed rendering supplies only the format Windows requested; disposal materializes any remaining formats. The HTML SourceURL header is retained so relative links retain their original base. `tests/ClipboardIntegrationTests` exercises real WinForms/raw CF_HTML Unicode round trips in a private, non-visible window station, never the user's interactive clipboard. It skips before any clipboard access if isolation is unavailable. That isolation was denied in the current test environment, so this live integration check remains unverified here.

Restored entries also request history/cloud exclusion. Clipboard-manager automatic expiry may be disrupted by any save/restore operation. Elevated applications are rejected. Identical text in another field of the same window cannot be distinguished by the text comparison. Use a Copy action when uncertain.

## Review tabs and finding rewrites

The review opens on the first non-empty tab in the fixed order below. If every tab is empty, Spelling remains selected. The tabs Spelling, Grammar, Punctuation, Wording and Formatting (German: Rechtschreibung, Grammatik, Satzzeichen, Formulierung, Formatierung) form one segmented bar at the top of the "Corrections in context" text box, since they filter only that section (text, bulk actions and correction list); the selected tab takes the review color (`--band`). Each has a count. A checked tab without corrections leaves the bar and appears next to it as its name and 0, without a button; running, failed and stopped tabs stay in the bar. Worth checking has a section of its own. Formatting fixes show the same old and new boxes as the corrections in context (old run with its decoration, new run without it), gray in the other tabs like their corrections. Chrome captures show Formatting 0. Where a text correction or a used wording touches a formatting run, the text wins and the formatting fix is not offered. With plain-text replacement the Formatting tab is disabled and its fixes stay gray. The full text remains visible in "Corrections in context":
- Only the selected tab's corrections are colored and clickable (red old, green new, each box with a thin border).
- Corrections of other tabs show the same old and new boxes in gray, with their accepted or rejected state. Clicking one opens its tab and briefly highlights it there (`openCorrection`).
- Sentences without a correction of the selected tab are muted (`sentenceEnds`, `showInline`). A sentence ends after `.`, `!`, `?` or `…` plus spaces, or at a line break.
- All correction boxes have the same box model without vertical padding, so switching tabs moves no word and no line.

Below the text, a footer inside the text box holds "Accept all", "Reject all" (selected tab only) and a progress bar with accepted and rejected counts of the selected tab. The correction list ("Show correction list") has one compact row per correction: a switch, old → new, and the sentence around it (`changeContext`); below 520 px list width the sentence moves under the change. Switching tabs preserves choices, and the revised text includes accepted corrections from every tab.

Service-supplied correction categories are matched to locally computed diff parts using original UTF-16 ranges. Missing labels fall back to punctuation for punctuation/quote/whitespace-only changes, spelling for a single changed word, and grammar otherwise. If one diff unit overlaps several classified ranges, the largest overlap wins, with source order breaking ties. Category labels never supply the edit positions: the local diff and minimal Unicode-safe patches remain authoritative.

Worth checking contains all finding kinds, each labelled (ambiguity, term misuse, contradiction, unsupported claim or logic gap). A finding offers "Use this wording" only when its first quote is non-empty and occurs exactly once, including overlapping occurrences. Choosing it creates an accepted replacement in the normal edit pipeline. Overlapping spelling/grammar corrections are superseded without losing their choices. "Undo wording" or rejecting the replacement restores those choices. Overlapping finding rewrites are mutually exclusive. Worth checking bulk actions affect only rewrites the user has activated, not every unchosen finding. Dismissing a finding also undoes its active rewrite. Rewrites that change line breaks are disabled, with the reason displayed beside the button. Existing HTML mapping and direct-editor safety checks apply; a rewrite that crosses formatting can be refused with the usual mapping error.

### Optional Ctrl+Alt+- formatting checks

Capture with Ctrl+Alt+- and check the text as usual. Formatting is checked automatically when copied HTML is available. Formatting suggestions appear in the Formatting tab and start accepted, like text corrections. Reject unwanted fixes before "Paste with formatting" or "Original formatting". These checks run locally and apply only to the Ctrl+Alt+- HTML clipboard path. They are skipped when the copy has a `<style>` block, class names, layout CSS or CSS that may draw a line (`text-decoration` or `text-decoration-line` with any value other than `none` or `initial`); Chrome's default `text-decoration-thickness`, `-style` and `-color` values on every copied element draw no line and are ignored (`DrawsCssDecoration`). A spot is offered only when its text occurs once in the capture.

The first rule handles a single edge space in simple explicit underline, strikethrough or link tags, where adjacent unformatted text makes the boundary clear. It preserves the text and moves the space outside that tag. Complex/nested formatting, CSS-dependent decoration, paragraph-end spaces, repeated spaces and ambiguous captures are skipped. A text correction touching the same space must be rejected before applying its formatting fix. Destination apps still control HTML paste rendering. Chrome direct editing is unchanged.
